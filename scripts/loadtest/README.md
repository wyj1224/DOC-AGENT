# 本地压测

用模拟的 DeepSeek（固定延迟）压测任务队列，衡量系统本身而不是大模型的速度。真实 LLM 和线上服务器不参与：线上有 nginx 限流，而且每次调用都会花钱。

## 怎么跑

```bash
# 1. 模拟 LLM：每次调用固定等待 2 秒，按 allowed_actions 依次调用工具后 finish
python scripts/loadtest/fake_llm.py --port 9100 --latency 2.0

# 2. 后端指向它（容器或本机均可），并导入强条 Excel
#    DEEPSEEK_BASE_URL=http://127.0.0.1:9100  DEEPSEEK_API_KEY=fake  LLM_MAX_CONCURRENCY=16
python -m app.cli.worker --concurrency 4

# 3. 压测：每个虚拟用户上传一份 Word，然后循环「提交一致性检查 → 等结果」
LOADTEST_DOCX=path/to/一致性测试集.docx LOADTEST_MODE=queue \
  locust -f scripts/loadtest/locustfile.py --host http://127.0.0.1:8000 \
  --headless -u 20 -r 1 -t 180s --csv results/queue_c4
```

`LOADTEST_MODE=sync` 改为调用阻塞的 `POST /agent/check`，作对照。locust 报告里的 `TASK end-to-end` 是从提交到任务进入终态的时间。

## 结果（2026-10-28）

环境：Apple M5 / Docker Desktop（10 CPU，8 GB），API 与 worker 用生产镜像各一个容器，PostgreSQL 16 容器。一致性检查任务每次 4 次 LLM 调用（3 步 ReAct + 1 次报告）。

### 系统自身开销（LLM 延迟 = 0，单用户，18 个任务）

| 环节 | 平均 |
|---|---|
| 一致性检查工具 `word_check_tool` | 229 ms |
| 其余步骤 | ~6 ms |
| 任务执行合计 | **279 ms** |
| 排队到被领取（worker 每 1 s 轮询） | 559 ms |

结论：线上一个任务几十秒的延迟几乎全部来自 LLM 调用。

### 20 并发用户，LLM 每次 2 s，3 分钟

| 模式 | 提交接口 p50 / p95 | 端到端 p50 / p95 | 完成任务 | 吞吐 |
|---|---|---|---|---|
| 队列，1 个 worker 槽位 | 49 ms / 12 s* | 53 s / 114 s | 17 | 5.7 任务/分钟 |
| 队列，2 个槽位 | 16 ms / 3.9 s* | 55 s / 81 s | 32 | 10.7 任务/分钟 |
| 队列，4 个槽位 | 13 ms / 140 ms | 40 s / 42 s | 61 | 20.5 任务/分钟 |
| 队列，8 个槽位 | 9 ms / 180 ms | 19 s / 23 s | 112 | 37.6 任务/分钟 |
| 同步 `/agent/check` | 9.4 s / 12 s | 9.4 s / 12 s | 198 | 66 任务/分钟 |

- 所有轮次共 698 个任务成功、0 个失败（另有 101 个是每轮结束时仍在排队、被脚本取消的）。
- 吞吐随 worker 槽位近线性增长（1 → 8 槽位约 6.6 倍）；模拟 LLM 记录的并发峰值始终等于槽位数，说明 LLM 并发被严格限制。
- 状态查询 `GET /agent/tasks/{id}` 在 ~25 次/秒下 p95 < 60 ms。
- 同步模式吞吐更高，是因为它的并发只受线程池和 LLM 上限（16）限制，没有排队；代价是每个请求占住一个 HTTP 连接和线程 9 秒以上，浏览器断开结果就丢失。队列模式用固定槽位换取可控的资源占用和 LLM 调用量。
- \* 1–2 个槽位时提交接口 p95 偏高，是测试开头 20 个上传同时解析 Word 拖慢了 API 进程（见下）。

### 发现并修复：并发上传

修复前，20 个用户同时上传 Word 时单次上传 p50 约 46 s（单独上传约 2.4 s），每秒启动 10 个用户时 25% 返回 500。定位到三个原因：

1. **解析算法**：python-docx 的 `paragraph.style` 每次都线性扫描文档全部样式，解析是 O(段落数 × 样式数)，一份文档读 130 万次 XML 属性。改为每份文档建一次样式 id → 名称映射（`paragraph_style_name`）。在本地 102 份文档上输出逐字节一致，解析从 2422 ms/份降到 600 ms/份（4.0 倍）。
2. **连接池耗尽**：`parse_word_tool` 在持有数据库连接期间解析，并发时连接池（5 + 10）耗尽，30 s 后报 `QueuePool limit ... reached`。改为「短事务建记录 → 不持连接解析 → 短事务写结果」。
3. **GIL**：解析在 API 进程内执行。生产配置改为每核一个 uvicorn 进程（`WEB_CONCURRENCY=2`），`init_db` 用 PostgreSQL advisory lock 防止多进程同时建表。

顺带修复：文档名记录成带随机前缀的存储文件名（会话标题乱码）；合并单元格去重用 `id()` 判断，lxml 代理对象被回收后 id 会复用，导致表格单元格被随机跳过（同一文档两次解析得到 2276 / 2272 个片段，修复后与 XML 实际单元格数一致）。

修复前后（20 用户，LLM 每次 2 s）：

| 场景 | 指标 | 修复前 | 修复后 |
|---|---|---|---|
| 平稳启动（1 用户/秒），8 槽位 | 上传 p50 | 49 s | **0.64 s** |
| | 提交接口 p95 / p99 | 180 ms / 9.7 s | **27 ms / 34 ms** |
| | 吞吐 | 37.6 任务/分钟 | **51.7 任务/分钟** |
| 突发（10 用户/秒），4 槽位 | 上传失败率 | 25 %（5/20） | **0** |
| | 上传 p50 | 47 s | 24 s（1 进程）/ **19 s（2 进程）** |
| | 吞吐 | 16.1 任务/分钟 | **22.1 任务/分钟** |

修复后 API 日志中 `QueuePool` 错误为 0。突发场景上传仍需排队：20 份文档同时到达时 CPU 是瓶颈，进一步改善需要把解析也放进队列异步执行。
